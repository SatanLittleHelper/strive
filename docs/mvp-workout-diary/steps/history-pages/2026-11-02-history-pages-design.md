# Дизайн H2 — страницы истории тренировок

## Контекст

Шаг H2 роадмапа «MVP дневника тренировок»: после завершения тренировки пользователь сейчас попадает на заглушку `/history` (`layout/section-placeholder`). Бэкенд истории (H1) готов, не хватает веба. H2 разблокирует P1 (состояния/валидация), P2 (e2e-сценарий) и P3 (README).

Страница деталей должна показывать подходы по упражнениям. Сейчас `WorkoutSession.results` — плоский список `SetResult[]`, а `GET /api/sessions/:id/summary` отдаёт только агрегаты. Группировку подходов делаем на бэкенде, в репозитории, и отдаём через расширенный `/summary` — клиент ничего не группирует. Поэтому H2 включает небольшую доработку контракта H1 (вертикальный срез API + web).

## Требования

- Вкладка «История» (`/history`) показывает список завершённых тренировок устройства: название, дата, краткая сводка «N упражнений · M подходов».
- Тап по строке открывает `/history/:id` — детали тренировки.
- Детали: шапка (название, дата, длительность, тоннаж) и карточки упражнений со списком подходов (вес × повторы, RPE, заметка). Страница делает один запрос — `GET /api/sessions/:id/summary`.
- `GET /api/sessions/:id/summary` дополнительно отдаёт `exercises` — упражнения тренировки с подходами, уже сгруппированные и упорядоченные.
- Состояния: загрузка (скелетоны), ошибка с «Повторить», пустая история, «тренировка не найдена» (404/400) — теми же общими компонентами, что на страницах каталога. Для `409` (сессия не завершена) показываем то же состояние «не найдена»: в истории таких сессий быть не должно.
- Навигацию менять не нужно: вкладка «История» уже в `NAV_ITEMS`, а `active-session.component.ts` после завершения уже делает `navigateByUrl('/history')`.

## Критерии успеха

- Завершённая тренировка появляется в списке, и её детали совпадают с записанными подходами.
- Подходы в деталях сгруппированы по упражнениям в порядке плана, внутри упражнения упорядочены по `setNumber`; упражнения без подходов не выводятся.
- Тоннаж, число упражнений и подходов в сводке считаются из того же сгруппированного вида и совпадают с суммой по подходам.
- Пустая история, ошибка сети и неизвестный id обрабатываются без падения страницы.
- Тесты API (нужен Docker), Playwright-спеки истории (chromium), `npm run typecheck`, `lint`, `npm test` зелёные.

## Рассмотренные подходы

1. **Расширить `/summary` полем `exercises`, группировка в репозитории (выбран).** Один запрос на страницу деталей, группировка и порядок на бэкенде, один источник расчёта агрегатов. Плюс — контракт H1 меняется, но БД и миграции нет.
2. Новая ручка `/sessions/:id/details` с отдельным типом. H1-контракт не трогается, но в API появляются две почти одинаковые ручки.
3. Сгруппировать в `GET /sessions/:id` вместо плоского `results`. Ломает активную тренировку, которая использует `results`, и выходит за рамки H2.

Список истории остаётся на `GET /api/sessions` (`WorkoutSession[]`); строка «N упражнений · M подходов» считается на клиенте из `results` простой функцией форматирования (уникальные `exerciseId`, длина массива).

## Дизайн

### Контракт (`libs/api-interfaces/src/workout-session.types.ts`)

```ts
export interface SessionExerciseResults {
  exerciseId: number;
  name: string;
  sets: SetResult[];
}

// SessionSummary получает поле:
exercises: SessionExerciseResults[];
```

Порядок `exercises` — как в плане тренировки; в `sets` — по `setNumber`; упражнения без подходов не включаются. После правок — `npx nx run api-interfaces:build`.

### Бэкенд

- `SessionRepository` (`apps/api/src/sessions/session.repository/`): новый метод `getFinishedExercises`-типа (имя уточнить в плане), который одним Prisma-запросом читает завершённую сессию устройства вместе с упражнениями плана и подходами этой сессии (`orderBy` по позиции упражнения и по `set_number`) и возвращает сгруппированный вид. Чужая/несуществующая сессия — `404`, незавершённая — `409` (как сейчас в `getFinished`). Доступ к ORM — только в репозитории.
- `toSessionSummary` (`session-summary/`) принимает сгруппированный вид: `exerciseCount` = число упражнений в `exercises`, `setCount` = сумма длин `sets`, `totalVolume` = сумма `weight × reps` с округлением до 2 знаков; сессия без подходов даёт нули и пустой `exercises`.
- Контроллер: `@Get(':id/summary')` использует новый метод репозитория вместо `getFinished` + плоского маппера.
- Тесты: репозиторий (интеграция с реальной БД: группировка, порядок, пропуск упражнений без подходов, 404/409), unit на `toSessionSummary`, обновление `sessions.http.spec.ts` для `/summary`. Детали — в тест-плане.

### Маршруты (web)

В `apps/web/src/app/app.routes.ts` заменить `history` (заглушка) на ленивый `HistoryListComponent` и добавить `history/:id` → `HistoryDetailsComponent`. Id приходит через `input.required<string>()` (как в `workout-details`, `withComponentInputBinding` уже включён).

### Файлы (новая папка `apps/web/src/app/history/`)

Структура по правилам dot-подпапок и barrel-файлов проекта:

- `history-list/` — компонент списка (`.ts`, `.html`), `index.ts`.
- `history-details/` — компонент деталей (`.ts`, `.html`), `index.ts`.
- `format-session-summary/` — чистые функции + `*.spec.ts` (Vitest): число уникальных упражнений и подходов для строки списка, склонения («упражнение/упражнения/упражнений», «подход/подхода/подходов») через `Intl.PluralRules('ru-RU')` по образцу `workouts/format-exercise-count`, длительность из `finishedAt − startedAt`, формат тоннажа.
- `history.constants.ts` — `MISSING_SESSION_STATUSES` (404, 400, 409) по образцу `workouts.constants.ts`.

### Данные (web)

В существующий `SessionsService` (`sessions/sessions.service/sessions.service.ts`) добавить методы на `httpResource` (как `getList`/`getDetails` в `WorkoutsService`):

- `getFinished()` → `GET /api/sessions` (поле `history` там уже занято историей упражнений — имя нового метода с ним не пересекается);
- `getSummary(id: () => string)` → `GET /api/sessions/:id/summary` с `encodeURIComponent`.

Отдельный запрос `GET /api/sessions/:id` для деталей не нужен.

### Состояния страниц

`getResourceViewState({status, isEmpty})` + `@switch`: loading → `tuiSkeleton` в `role="status"`; error → `<app-error-state (retry)="reload()">`; empty → `<app-empty-state>`; ready → контент. В деталях ошибки из `MISSING_SESSION_STATUSES` → `app-empty-state` «Тренировка не найдена» со ссылкой назад.

### UI (Taiga в приоритете, Tailwind — только раскладка)

- Список: `tuiCell` / `tuiCardLarge` на строку, название и дата — `tuiTitle`, сводка — вторичный текст, строка — `routerLink`. Дата `DatePipe 'dd.MM.yyyy'`.
- Детали: ссылка `← История` (`tuiLink`), шапка `tuiCardLarge` + `tuiHeader`, `tuiBadge` для длительности/тоннажа; карточка упражнения — `tuiCardLarge` со списком подходов через `tuiCell`; RPE и заметка показываются, только если заданы.
- Собственную вёрстку не вводим; если какого-то блока в Taiga нет, сверяемся с документацией (`context7`).

### Вне скоупа H2

Пагинация (идея в `docs/ideas.md`), тоннаж в строке списка, удаление/редактирование записей, графики. Валидация ввода, универсальные пустые состояния и полировка — шаг P1, полный сценарий «старт → запись → завершение → история» — P2.

## Тестирование

По правилам проекта юнит-тесты компонентов не пишутся. Слои:

- **Интеграция/API (Testcontainers):** репозиторий и `/summary` — см. «Бэкенд».
- **Vitest (юнит):** `toSessionSummary` (агрегаты по сгруппированному виду, нули для пустой сессии) и `format-session-summary` (склонения на границах 1/2/5/11/21, подсчёт для строки списка, длительность, формат тоннажа).
- **Playwright:** `apps/web-e2e/src/history.spec.ts` на моках (`page.route`) — список, пустая история, ошибка + «Повторить», переход в детали, 404 и 400; расширить `support/session.fixtures.ts` (`makeSession` с заполненным `finishedAt`, `mockSessionList`, `mockSummary`). Плюс проверка на реальном API и seed по образцу `session.fullstack.spec.ts`.
- Проверить, что `layout.spec.ts` (строки с `/history` и заголовком «История») не ломается: оставить `h1 «История»` и замокать `/api/sessions`.

## Открытые уточнения для плана

- Имя и сигнатура нового метода репозитория; точная форма Prisma-запроса (вложенный фильтр `set_results` по сессии) — по схеме `apps/api/prisma/schema/*.prisma`.
- Могут ли в `set_result` попасть подходы упражнения, которого нет в плане тренировки (FK ведёт только на `exercise`); если да — решить, включать ли такие подходы в `exercises`, чтобы агрегаты не расходились с прежним расчётом.
- Нужен ли отдельный компонент для подходов упражнения или достаточно шаблона деталей — решить при разбиении на задачи.
