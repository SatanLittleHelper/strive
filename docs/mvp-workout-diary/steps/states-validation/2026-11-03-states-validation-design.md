# P1 — состояния загрузки и валидация формы подхода — дизайн

## Контекст

Большая часть состояний уже сделана: список тренировок, детали, история и экран сессии умеют скелетон, пусто и ошибку с «Повторить» (общие `shared/error-state`, `shared/empty-state`, выбор состояния через `api/resource-view-state`). В P1 остаются два пробела:

1. Экран сессии при загрузке показывает текст «Загрузка тренировки…» вместо скелетона.
2. Невалидный ввод подхода (`sessions/set-row`) даёт один общий блок ошибки, а валидация вручную ведётся строками в `validateSetInput` поверх `ngModel`.

Почему меняем подход к п. 2: ручное поле `field` и сигнал `invalidField` дублируют то, что формы Angular дают из коробки (`invalid`, `touched`, `errors`), а Taiga UI штатно показывает ошибки через `tui-error` и подсвечивает `tui-textfield` по состоянию контрола. Правила проекта для Angular 22 без принятых Signal Forms (в коде нет `@angular/forms/signals`) требуют Reactive Forms (`NonNullableFormBuilder`), а не `ngModel`.

Вне скоупа P1:
- Главная: на ней пока почти ничего нет, скелетон и ошибка для статуса API не делаем.
- Разные сообщения на 400/409/5xx при сохранении подхода и детали ошибок по полям с бэкенда.
- Переход на Signal Forms.

## Требования и критерии успеха

- R1. Экран сессии: состояние `loading` рисуется скелетоном (`tuiSkeleton`, `role="status"`, как на списке тренировок), а не текстом.
- R2. Форма подхода построена на Reactive Forms. При попытке сохранить с невалидным вводом под каждым невалидным полем (вес, повторы, RPE, заметка) виден текст ошибки (`tui-error`), поле подсвечено состоянием контрола; запрос не уходит. Ошибка исчезает, как только значение исправлено.
- R3. Правила проверки берутся из `SET_RESULT_LIMITS` (`libs/api-interfaces`): вес от 0 до `weightMax`, не более двух знаков после запятой; повторы — целое от `repsMin` до `repsMax`; RPE — необязательное целое от `rpeMin` до `rpeMax`; заметка — не больше `noteMaxLength`. Новых констант и изменений бэкенда нет.
- R4. Ошибка сервера при сохранении по-прежнему показывается единым блоком «Не удалось сохранить подход…» и не подсвечивает поля.

## Подходы

**Форма.** (a) Reactive Forms: `FormGroup` из `NonNullableFormBuilder`, валидаторы Angular (`required`, `min`, `max`, `maxLength`) плюс два чистых кастомных (`integer`, `maxDecimalPlaces`), ошибки через `tui-error` и `tuiValidationErrorsProvider`. (b) Signal Forms. (c) Оставить ручную валидацию с `field`. Берём (a): по правилам проекта это единственный вариант, пока Signal Forms не приняты; (b) не оправдан ради одной формы; (c) отклонён замечанием.

**Значения формы.** Источник значений по умолчанию (`initial`: сохранённый результат, подстановка из «Прошлых тренировок», план) остаётся вычисляемым сигналом. Единственный владелец введённых значений — `FormGroup`: побочный эффект `reset(initial)` срабатывает при смене источника, если форма ещё не изменялась пользователем (`pristine`) или пришёл новый запрос подстановки (`fillRequest`). Это сохраняет текущее поведение «введённое не затирается пересчётом значений по умолчанию» без ручного сравнения `isSameFormValues`.

## Дизайн

- `sessions/set-form.validators.ts` (чистые функции): `integer`, `maxDecimalPlaces(places)` и константы наборов валидаторов `WEIGHT_VALIDATORS`, `REPS_VALIDATORS`, `RPE_VALIDATORS`, `NOTE_VALIDATORS`, построенные от `SET_RESULT_LIMITS`.
- `sessions/set-row` — `FormGroup` с контролами `weight` и `rpe` типа `number | null` (так отдаёт `tuiInputNumber`), `reps` и `note`; шаблон на `[formControl]`/`formControlName`, под каждым полем `tui-error`; `tuiValidationErrorsProvider` с русскими сообщениями (обязательное поле, не меньше/не больше, только целое число, не более двух знаков после запятой, не больше N символов).
- Сохранение: если форма невалидна — `markAllAsTouched()`, запрос не отправляется; иначе значения превращаются в `SaveSetResultRequest` чистой функцией (пустая заметка → `null`, пустой RPE → `null`). Закрытие редактора сбрасывает `touched`, чтобы при повторном открытии ошибок не было.
- `validateSetInput`, `RawSetInput`, `SetInputValidation` и ручной `error`-блок для ошибок ввода удаляются; `isSameFormValues` удаляется, если после правки не останется использований. Блок `tuiNotification` остаётся только для ошибки сервера (R4).
- `sessions/active-session/active-session.component.html` — ветка `loading` заменяется скелетоном по образцу `workouts/workout-list/workout-list.component.html`.

## Обработка ошибок

Невалидный ввод — ошибки под полями, запрос не уходит. Ошибка сервера — единое сообщение в блоке `alert` без подсветки полей. Пустой вес — ошибка «обязательное поле» под полем веса.

## Тестирование (слои — по `rules/base/testing.md`, детали в тест-плане)

- Юнит: наборы валидаторов (`WEIGHT_VALIDATORS` и др.) через `FormControl` на каждой границе (`weightMax`, `weightMax+`, дробные знаки, повторы `repsMin-1`/`repsMax+1`/дробные, RPE `rpeMin-1`/`rpeMax+1`, пустой RPE и заметка допустимы, заметка `noteMaxLength+1`), кастомные `integer` и `maxDecimalPlaces`, функция преобразования значений формы в запрос. Тесты бывшего `validateSetInput` переносятся на эти функции. Компонентных юнит-тестов нет (правило проекта).
- Playwright (моки, `session.fast.spec.ts`): скелетон загрузки сессии; для веса, повторов и RPE — текст ошибки под полем при невалидном вводе, запрос не уходит, ошибка исчезает при исправлении, повторное открытие редактора без ошибок, сохранение после исправления, ошибка сервера без ошибок под полями.
- Интеграционный слой API не меняется.

## Риски

- Перенос `set-row` с `ngModel` на Reactive Forms затрагивает подстановку из «Прошлых тренировок», предзаполнение и поздно пришедшую историю: существующие e2e (`предзаполнение подхода`, `история подходов`) должны остаться зелёными без правок.
- Эффект `reset(initial)` не должен затирать ввод пользователя при позднем приходе истории — проверяется существующим кейсом «поздно пришедшая история не затирает введённый вес».
- Сообщения `tui-error` зависят от токена `TUI_VALIDATION_ERRORS`; точный вид провайдера сверяется по документации Taiga (`tuiValidationErrorsProvider`) на этапе плана реализации.
