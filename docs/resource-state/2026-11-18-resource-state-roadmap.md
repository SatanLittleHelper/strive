# Роадмап: единый компонент состояний ресурса

## Context

**Проблема.** Каждая страница, читающая `httpResource`, повторяет один и тот же `@switch (state())` с четырьмя ветками: скелетон загрузки, `app-error-state`, `app-empty-state`, содержимое. Дублируются тексты, разметка `role="status"` и подключение `getResourceViewState`. Пять страниц: `history-list`, `history-details`, `workout-list`, `workout-details`, `active-session`.

**Текущее состояние.** Общие `app-error-state`, `app-empty-state` и хелпер `getResourceViewState` уже есть, но склеиваются вручную на каждой странице. Компонент `app-resource-state` (`shared/resource-state`) появится в шаге H1 роадмапа `workout-feedback` и сразу подключается к истории упражнения.

**Целевое состояние.** Все пять страниц используют `app-resource-state`: состояния загрузки/ошибки/пусто описываются в одном месте, страница передаёт только состояние, при необходимости свои тексты пустого состояния, ошибки и подпись загрузки (по умолчанию «Нет данных», «Не удалось загрузить данные» и «Загрузка»), содержимое — через проекцию; загрузка по умолчанию — спиннер Taiga, при необходимости заменяется проекцией `[loading]` (скелетоном). Для нестандартных случаев компонент принимает проецируемое содержимое пустого состояния и ошибки.

**Жёсткие ограничения.**

- Поведение и тексты страниц не меняются: существующие e2e остаются зелёными без правок ожиданий (там, где страница сегодня показывает свой текст ошибки или подпись загрузки, она передаёт его явно).
- Серверный контракт, схема БД, миграции не меняются.
- Компоненты Taiga UI в приоритете, только тёмная тема, юнит-тесты компонентов не пишутся (`CLAUDE.md`).
- Шаги не начинаются, пока в `main` нет компонента из шага H1 роадмапа `workout-feedback`.

**Почему роадмап, а не один план.** Страницы независимы, и после каждого шага приложение работает: непереведённые страницы продолжают жить на старой разметке.

**Допущения оценки.** Один разработчик, знающий стек; «агент» — календарное время с ревью человека. Оценки грубые.

## Архитектура (целевая)

- `ResourceStateComponent` (`app-resource-state`): входы `state: ResourceViewState`, `emptyMessage`, `loadingLabel`, `errorMessage` (все с умолчаниями, переопределяются), выход `retry`; загрузка — `tui-loader`, проекция `[loading]` — замена (скелетон), содержимое без селектора — состояние `ready`, `[empty]` и `[error]` — замена стандартных пустого состояния и ошибки.
- Страница считает `state` через `getResourceViewState` и больше не содержит `@switch` по состояниям.

## Сквозные риски

- `active-session` правят шаги `R1`, `R2`, `T1` роадмапа `workout-feedback`: `S3` выпускать после них или с ребейзом, иначе конфликты в шаблоне и компоненте.
- Страницы показывают разные тексты ошибки и подписи загрузки («Загрузка тренировки», «Загрузка истории» и т.д.) и скелетоны своей формы: тексты передаются явно, скелетон — проекцией `[loading]`, иначе существующие e2e-локаторы и внешний вид изменятся.
- На `workout-details` и `history-details` ошибка 404 показывается как пустое состояние «Тренировка не найдена»; без проекции `[empty]`/`[error]` из шага `S2` это не выразить.

## Verification

Роадмап не содержит кода: проверка выполняется в плане каждого шага (scoped-прогоны в TDD-цикле и один итоговый проход `build`, `typecheck`, `lint`, `test`, `e2e`).
